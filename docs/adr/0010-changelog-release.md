# 変更履歴とタグ・Release の作り方

手順は `docs/release.md`。

## 決定

| 項目 | 決定 |
|---|---|
| 変更履歴 | リポジトリ直下の `CHANGELOG.md`。日本語で、使う人から見える変化を中心に書く。新しい版が上、見出しは `## <版> — 日付` |
| 項目の元 | PR 本文の「## 変更履歴」の欄。空なら PR の件名、「なし」なら載せない。PR テンプレートに欄を置く |
| 書くとき | 版を上げるときにまとめて書く。`scripts/bump-version.sh <版>` が前の版のタグ以降にマージした PR を集めて節を作り、版の表記もすべて書き換える。節は人が読んで直してからコミットする |
| タグと Release | main の `MARKETING_VERSION` に対応するタグ `v<版>` がなければ、Actions(`release.yml`、ubuntu)がタグと GitHub Release を作る。本文は `CHANGELOG.md` の節。版上げを含む PR のマージがきっかけになる |
| 配布物 | Release に zip を付けるのは手作業(`gh release upload`)。CI に署名の証明書を置いていないため |
| 過去の版 | 0.1.0〜0.7.0 の変更履歴は `docs/plan.md` と git log から書き起こした。タグは後から下のコミットに打つ(どれもその版の `MARKETING_VERSION` を持つ)。0.7.0 はこの仕組みが作る |

過去の版のタグ先。版を上げた時期が版ごとに違う(区切りの最初に上げた版と、最後に上げた版がある)ので、`docs/plan.md` の節の区切りに合わせて選んだ。

| タグ | コミット | 区切り |
|---|---|---|
| v0.1.0 | `b48a2cb` | フェーズ1〜3(2026-11-07) |
| v0.2.0 | `ee107cd` | フェーズ3.5(線の種類・多言語化など) |
| v0.3.0 | `5e77246` | フェーズ4(キャプチャ) |
| v0.4.0 | `e619e05` | 切り抜きの px 指定・枠線と影・スタンプの種類(0.5.0 に上げる直前) |
| v0.5.0 | `27d236e` | Quick Look |
| v0.6.0 | `d8f5e1e` | CLI・MCP・グリッド・入れ方の手順(PR #8 のマージ) |

## 理由

- OSS にするので、版ごとのタグと Release が要る。ADR 0008 でも CLI は App と同じタグで出すと決めている
- コミットと PR の件名は日本語の自由な文で、Conventional Commits ではない。release-please・git-cliff は規約に合わないコミットを読み飛ばすので、使うにはコミットの書き方から変える必要がある。PR 本文の欄なら今の書き方のまま、利用者向けの文を別に書ける
- PR のマージごとに Actions が `CHANGELOG.md` へ追記して main にコミットする形は採らない。公開後にブランチ保護を入れると、Actions からの main への push が通らなくなるおそれがある。版を上げるときに PR の中で書けば、main へ直接書き込むのはタグと Release だけで済む
- GitHub の自動生成(`--generate-notes`)だけだと、変更履歴がリポジトリに残らず、件名(開発者向けの言い方)がそのまま並ぶ
- タグの有無で判定するので、同じ版で何度動いても Release は1つ。版の数字を比べる方式と違い、取りこぼしたときは手で動かせば追いつく(`workflow_dispatch`)
- install-release-workflow(claude-release-workflow)は導入先の CHANGELOG を書かず、開発の流れそのものを置き換えるので、目的に合わない

## 見直す条件

- 共同開発者が増え、PR 本文の欄が書かれなくなったとき(CI で欄の有無を確かめる)
- Developer ID と公証を CI で行うようになったとき。zip の作成と添付も Actions に移す
- 版を上げずに出したい変更(LP だけなど)にもタグが欲しくなったとき
